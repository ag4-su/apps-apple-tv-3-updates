# Выпуск приложения магазина Apple TV

Работайте из основного репозитория `apple-tv`: код упаковщика находится в `build/release.py`, а метаданные приложения — в `modules/<module>/module.json`. Этот репозиторий содержит опубликованный каталог и подпись; ZIP и изображения хранятся в GitHub Releases `ag4-su/apps-apple-tv-3-updates`.

## Ограничения

- Выпускайте только реально предназначенную пользователям версию. Не подписывайте производственным ключом тестовые или вымышленные каталоги и не изменяйте уже опубликованную версию.
- Приватный ECDSA P-256 ключ остаётся на машине автора вне обоих репозиториев. Не копируйте его на Mac-сборщик, приставку, в журналы, Git или GitHub. Открытый ключ — `modules/core/res/catalog-public.pem` в основном репозитории.
- Не редактируйте `catalog.json` или его бинарную DER-подпись вручную. Упаковщик проверяет ключ, предыдущий каталог и пакет, увеличивает `serial` и подписывает точные байты каталога.
- Инсталлятор сейчас поддерживает приложения, совместимые с уже установленной основой. Не объявляйте обновление основы, магазина или помощника доступным для установки, пока соответствующий механизм не реализован и не проверен на устройстве.
- Не удаляйте и не перезаписывайте посторонние файлы репозитория обновлений, в том числе `youtube.json`.

## Подготовка

1. Убедитесь, что пользователь запросил выпуск, приложение готово и `version`, `core` и прочие поля его `module.json` соответствуют реальному изменению. Для новой версии при необходимости обновите метаданные в основном репозитории. `dataCompat` — самая ранняя версия, способная прочитать данные выпуска; не угадывайте её.
2. На Windows используйте Git Bash и настроенный Mac домашней лаборатории: `build/build.sh` сам делегирует сборку на Mac без передачи приватного ключа. Нужны Python, OpenSSL, Git и авторизованный `gh` с правом публикации. Параметр `--key` указывает на локальный приватный ключ.
3. Клон этого репозитория должен быть на `main`, совпадать с `origin/main`, а файлы каталога — не иметь локальных изменений. Обновляйте клон только безопасным fast-forward; не уничтожайте пользовательские изменения. Создайте непустой UTF-8 файл заметок и выберите ещё не существующий каталог результата.

## Команды

Запускайте из основного репозитория, подставив реальные значения:

```bash
python build/release.py prepare <module> \
  --updates <путь-к-клону-репозитория-обновлений> \
  --key <локальный-приватный-ключ.pem> \
  --notes <utf8-файл-заметок> --data-compat <версия> \
  --output <новый-каталог-результата>

python build/release.py publish \
  --prepared <каталог-результата> \
  --updates <путь-к-клону-репозитория-обновлений>
```

`prepare` пересобирает выбранный модуль, проверяет метаданные бандла, создаёт ZIP и подписанный каталог, но ничего не публикует. Для витрины доступны `--featured`, `--recommend` и до восьми `--screenshot <PNG/JPEG>`; `--clear-screenshots` удаляет ранее опубликованные скриншоты. Без этих флагов существующие рекомендации и скриншоты сохраняются.

Перед `publish` проверьте подготовленные `release.json`, заметки и запись версии в каталоге. `publish` проверяет подпись и хеши ассетов, создаёт GitHub Release и отправляет подписанный каталог в `main`, не изменяя локальный индекс и рабочее дерево. После успешной публикации обновите клон fast-forward перед следующим выпуском. Если Release создался, а отправка каталога не удалась, сначала выясните реальное состояние Release и `origin/main`; не удаляйте Release и не повторяйте публикацию вслепую.

Проверьте установленный каталог и загрузку пакета на приставке; применение установки требует подтверждения и перезапуска меню. Указывайте только реально проверенный результат: переустановка той же версии не доказывает обновление между версиями, а штатная установка не доказывает восстановление после сбоя.
